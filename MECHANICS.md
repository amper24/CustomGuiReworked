# CustomGuiReworked — механики

## Скелет (тип слотов)

Каждый GUI описывает **скелет** — тип для каждого слота:

| Тип | Поведение | Сохраняется |
|---|---|---|
| `DESIGN` | декорация; содержимое из `design` GUI; клик не двигает предметы, но вызывает команды и `GuiSlotClickEvent` (кнопки) | нет |
| `CONTAINER` | полноценный слот хранилища | да |
| `CRAFT` | слот «крафта» (семаантика для кастомных систем) | да |
| `RESULT` | предметы можно только забирать; любая постановка блокируется (курсор, цифровые клавиши, свап с офхендом, drag, shift-перенос из нижнего инвентаря) | нет |
| `FUEL` | как CONTAINER, для механик «топлива» | да |

Персистятся только `CONTAINER`/`CRAFT`/`FUEL`
(`GuiHolder.isPersistable`). Предметы RESULT-слота — это «продукт»,
который не должен восстанавливаться при повторном открытии.

Тип слота читается из `skeleton` в `tables/<name>.yml`
(старые значения `design_0`, `container_3` и т.п. распознаются).

## Хранилище

> **Известная семантика мульти-зрителей:** у каждого зрителя свой
> экземпляр инвентаря (открытие не разделяет один inventory-объект,
> как ванильный сундук). Запись — дифом по baseline каждого зрителя,
> поэтому одновременная правка одного слота двумя игроками не затирает
> чужие изменения в других слотах; но одновременный «забор» одного и
> того же предмета двумя зрителями не защищён (как и в большинстве
> GUI-фреймворков с отдельными инвентарями). Для торговых автоматов
> это неактуально (предметы-«продукты» лежат в RESULT и не персистятся).

```
StorageKey = (StorageType, owner, table)
  BLOCK    owner = "world:x,y,z"
  PERSONAL owner = имя игрока
  TEAM     owner = команда (scoreboard, fallback "default")
  GLOBAL   owner = ""
  TEMPORARY owner = UUID игрока (диск не используется)
```

Слой `StorageService`:

1. **Один выделенный I/O-поток** (`CguiStorageIO`): весь ввод-вывод
   последователен, основной поток диска не касается.
2. `preload(key, ready)` — чтение с диска на I/O-потоке; `ready`
   (сборка/открытие инвентаря) выполняется обратно на основном потоке.
   Открытие GUI не фризит сервер на файловой системе.
3. `load(key)` — из кэша (`StorageView`), при промахе — синхронное чтение
   (используется после `preload`, фактически уже попадание в кэш).
4. Запись — **дифом по baseline** (`GuiHolder`): на следующий тик после
   клика (когда Bukkit уже применил изменение) содержимое слотов
   сравнивается с базовой линией, в хранилище идут только реально
   изменённые слоты — параллельные сессии других игроков не затираются.
5. **Коалесинг**: изменения в пределах `storage.coalesce-ms` (по умолчанию
   1000 мс) схлопываются в одну запись; `saveNow(key)` (закрытие/выход)
   отменяет отложенную задачу и пишет немедленно.
6. **Повтор при ошибке I/O**: неудачная запись остаётся `dirty` и
   ретраится через 5 с; автосейв каждые `storage.autosave-ticks`
   (по умолчанию 600) — дополнительная подстраховка.
7. `flushAll()` — при `onDisable`; сначала всем игрокам закрываются все
   меню плагина (рантайм-GUI, редактор, менеджер) — их обработчики закрытия
   синхронно делают финальный диф и `saveNow`, пока I/O-поток жив (это также
   исключает дюп из меню, оставшегося открытым после выключения плагина);
   экран дизайна редактора снимается синхронно; затем ожидание I/O-потока
   и синхронная дозапись всего грязного + флаш регионов.

Форматы на диске (совместимы с путями 1.x):

- `data/players/<игрок>_<таблица>` — JSON-массив строк;
- `data/teams/<команда>_<таблица>`;
- `data/globals/<таблица>`;
- `<мир>/CustomGuiReworked/blocks/<x/16>_<z/16>.json` —
  `{ "world:x,y,z": { "tables": { "<таблица>": ["n1:...", ...] } } }`.

Все записи атомарны (**уникальный** `.tmp-<uuid>` + `ATOMIC_MOVE`,
фолбэк на обычный move) — параллельные записи одного файла не затрут
временные файлы друг друга. Осиротевшие после жёсткого краха `.tmp-*`
подметаются: для `data/` и `tables/`,`custom/` — при загрузке плагина,
для регион-файлов блоков — при первом обращении к региону. Блок-регионы кешируются в памяти с локом
на регион, пишутся тем же I/O-потоком с коалесингом 500 мс и повтором
при ошибке; при выгрузке мира (`WorldUnloadEvent`) регион флашится
и выгружается из кэша.

Миграция 1.x: элементы-объекты (старый NBTAPI-JSON) конвертируются
при чтении через `LegacyPayloads` и записываются обратно в новом
формате. Без NBTAPI — упрощённый разбор (тип, количество, damage,
название, lore, CMD).

## Кодеки предметов

Payload = `<тег>:<данные>` (разделитель `:` обязателен — Base64 у `b2`
сам по себе двоеточий не содержит):

- `n1:` — NBTAPI (`NBTContainer.setItemStack/getItemStack`);
- `b2:` — нативный Paper `ItemStack.serializeAsBytes()` + Base64
  (основной fallback без NBTAPI);
- `b1:` — ранний формат 2.1.x (JSON-карта через `ItemStack.deserialize(Map)`),
  только читается, новыми данными не пишется.

Тег фиксируется при записи → данные читаются тем кодеком, которым
записаны, независимо от активного кодека (все три кодека регистрируются
как читатели при включении). Активный кодек выбирается при включении:
NBTAPI есть → `n1`, нет → `b2` (с предупреждением в лог).

## Блоки (ItemsAdder / CraftEngine)

`BlockHookManager` при включении: для каждого установленного
плагина (ItemsAdder, CraftEngine) **рефлективно** загружает хук и
регистрирует его слушатели. Без плагина — класс не загружается,
жёсткой зависимости нет.

- Интеракция (ItemsAdder — любой клик по custom block; CraftEngine —
  только правый клик) → `dispatcher.onBlockInteract`: GUI по ID блока
  (реестр O(1), без учёта регистра, fallback на суффикс после `:`) →
  `GuiOpener.openForPlayer(player, gui, blockLocation)` → событие
  отменяется.
- Разрушение блока → (1) **синхронно фиксируется актуальное содержимое
  открытых на блоке инвентарей в кэше региона** (анти-дюп: предмет,
  забранный на курсор в пределах окна коалесинга, уже не в слоте и не
  должен выпасть второй раз); (2) блок помечается «уничтожаемым»,
  открытые на нём интерфейсы закрываются **до** удаления данных (их
  обработчик закрытия в этом случае не пересохраняет таблицы);
  (3) предметы всех таблиц дропаются из актуализированного кэша;
  (4) данные региона и кэш удаляются.
- Запись в блок-хранилище при выгруженном мире не теряется молча:
  операция помечает данные грязными и повторяется после загрузки мира;
  при выгрузке мира регион флашится на диск.

## Редактор

`EditorSession` (на игрока): GUI + активный промпт
(`TITLE` / `BLOCK_ID`). Экраны: MAIN, SIZE, SKELETON, DESIGN,
STORAGE, BLOCKS. Клики по верхнему инвентарю отменяются по
умолчанию (панели редактора — служебные).

Исключение — экран DESIGN: предметы дизайна берут из своего
инвентаря. Клик по своему инвентарю разрешён (взять предмет на
курсор и положить его в дизайн-слот), shift-клик и драг раскладывают
предмет ванильной механикой. Пустые дизайн-слоты закрыты панелью
«Пусто», а для ванили такой слот «занят» — поэтому панели на время
переноса снимаются (`releasePane`/`releaseEmptyPanes`), а
`captureDesign` возвращает их на место (там же снимается дизайн,
возвращаются предметы, случайно попавшие в служебные слоты, и
восстанавливаются панели скелета). Double-click запрещён: он собрал
бы на курсор предметы самого дизайна. Пересъёмка дизайна — на
следующем тике и синхронно при закрытии экрана. Чат-промпты
отменяются сообщением `/cancel`. Каждое действие сразу
`registry.save(gui)`.

## События API

- `GuiOpenEvent` (Cancellable, до `openInventory`) — содержит собранный
  инвентарь и фактический `StorageKey`/тип хранилища (с учётом override);
- `GuiCloseEvent` — после обработки закрытия, с тем же `StorageKey`;
- `GuiSlotClickEvent` — клик по верхнему инвентарю, включая дизайн-кнопки:
  `getClick()`, `getAction()`, `getCurrentItem()`, `getCursor()`,
  `getHotbarButton()`, `getHandle()`. `setCancelled(true)` запрещает только
  привязанные команды; `setInteractionCancelled(true)` дополнительно
  отменяет сам клик Minecraft;
- `GuiDragEvent` (Cancellable) — растаскивание предметов по слотам
  (`getTopSlots()`, `getHandle()`). Перетаскивание по дизайн/result-слотам
  блокируется плагином до события.

## Команды слотов

`/gui command add <slot> <gui> [delay] <cmd...>` →
`SlotCommand(slot, command, delay)`. При клике:

1. `GuiSlotClickEvent` (отмена → команды не выполняются;
   interaction-cancel блокирует и сам клик);
2. команды срабатывают и на дизайн-слотах (кнопки), и на слотах хранилища;
3. `Bukkit.dispatchCommand` с плейсхолдерами `%player%`, `%slot%`;
   опционально `setOp` на время выполнения
   (`commands.execute-as-op`, по умолчанию выключено).

## Меню управления

`/gui` без аргументов (право `cgui.command`) открывает
`ManagerMenu` (45 слотов):

- список GUI (27/страница, пагинация; иконка = источник:
  книга — `tables/`, стеллаж — `custom/`, глаз — только память);
- **поиск в чате**: клик по кнопке «Поиск» закрывает меню и переводит
  сессию в режим ввода (`ManagerSession.InputMode.SEARCH`); следующее
  сообщение становится фильтром, после чего меню открывается заново;
  `/cancel` отменяет ввод;
- **создание** (`cgui.create`): клик → меню закрывается → имя в чате
  (`InputMode.CREATE`) → `registry.create` + редактор; `/cancel`
  возвращает к списку;
- **опции GUI** (ПКМ): предпросмотр (обычное открытие), редактор,
  перечитать файл, сведения, удаление (`cgui.delete`,
  «зарядка» 5 секунд — двойной клик);
- состояние игрока — `ManagerSession` (страница, поиск, создание,
  подтверждение удаления); `ManagerHolder` хранит «слот → имя GUI»,
  зафиксированное при отрисовке.

## Язык (lang/)

Строки интерфейса лежат в `lang/en.yml` и `lang/ru.yml` (секция
`language:`), активный язык — `language` в `config.yml`. Поиск значения
идёт по цепочке: файл выбранного языка → `lang/en.yml` на диске →
`lang/en.yml` из jar (ключи, которых нет на диске, не показываются как
`editor.someKey`). Форматирование — legacy-коды `§`, подстановка — `%s`.

В каждом файле есть ключ `lang-version`. При запуске плагин сравнивает
версию файла на диске с версией ресурса в jar и, если в jar она больше,
обновляет файл (прежняя копия остаётся рядом как `<имя>.yml.bak`).
Так правки формулировок и оформления заголовков доходят до серверов,
где файл был создан раньше. Автообновление выключается через
`language-auto-update: false` в `config.yml` — тогда выводятся только
уведомления в логе.

## Регистрация GUI из других плагинов

`Gui.Source`: `TABLE` (файл в `tables/`), `CUSTOM` (файл в
`custom/`), `RUNTIME` (без файла). `GuiRegistry.register(gui,
persist)` заменяет GUI с тем же именем (файл старого источника
удаляется, пишется новый) и обновляет блок-индекс; данные
хранилища не трогает — имя таблицы (`gui.fileName()`) не меняется,
поэтому уже сохранённые инвентари остаются на месте.
API: `GuiService.registerGui` / `unregisterGui` / `sourceOf` /
`getGuis`, `openGui(player, name, StorageType)` (подмена типа
хранилища на время одного открытия), `getOpenGui(player)`
(карта «игрок → открытое GUI» в `GuiOpener`).

## Интеграции Skript / Denizen

Обе — softdepend + тумблер в `config.yml` (`integration.*`);
регистрация происходит один раз при включении Skript/Denizen
(слушатели `PluginEnableEvent/PluginDisableEvent` на случай,
если скриптовый плагин включается позже).

- **Skript**: события `on cgui open/close/click/drag` через
  `SimpleEvent` + `EventValues` (event-player, event-string,
  event-number), условия/выражения/действия — стандартные классы
  `ch.njol.skript`.
- **Denizen**: события `on cgui open/close/click/drag` — подклассы
  `BukkitScriptEvent`, регистрация `ScriptEvent.registerScriptEvent(Class)`,
  контекст `context.player/gui/slot` (у drag — `context.slots`);
  теги — `PseudoObjectTagBase` + `TagManager.registerStaticTagBaseHandler`
  (псевдо-объект `cgui`).
